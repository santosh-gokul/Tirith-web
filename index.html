Abstract Summary

Kernel-level anti-cheats effectively stop malicious player behavior in competitive games, but raise severe user privacy concerns by installing unverifiable components at privileged modes (Ring-0 in x86).

Tirith resolves this by sandboxing games inside Protected Virtual Machines (pVMs) without compromising cheating detection or rendering performance—making user privacy a first-class citizen on personal computers.

System Overview & Split Responsibility

Comparing traditional kernel anti-cheat architecture against Tirith's VM-based sandboxing with split responsibility.

Overview of the VM-based sandboxing with split responsibility architecture (G: guest; H: host).

1 Zero Compromise on Protection Primitives

Even without kernel driver access on the host, Tirith does not compromise on security primitives:

  • In-Guest Protection: Developer anti-cheat logic retains full kernel privilege inside the isolated guest LibOS to perform game-specific memory scanning, code integrity checks, and asset manifest verification.
  • Hypervisor Platform Attestation: System-level checks (e.g. host kernel integrity, signed driver policies, Secure Boot state) are offloaded to the trusted first-party hypervisor, which the game attests before authorizing online sessions.
2 The Challenge: Graphics & Display Overhead

While VM sandboxing solves host privacy and cheat isolation, standard virtualized gaming introduces severe performance bottlenecks:

  • Paravirtualized GPU Overheads: Traditional GPU paravirtualization (e.g. VirGL/virtio-gpu) relies on command stream encode/decode, context switching, and frequent VM-exits, reducing frame rates by 1.4× to 13.3× compared to native.
  • Display & Input Frame Latency: Cross-VM frame buffer copying and naive event forwarding add prohibitive input-to-display latency unsuited for real-time competitive multiplayer games.

Technical System Innovations

A Guest LibOS & Graphics Translation
Gramine-VM
OpenGL to EGL Redirector (egl-redirect): Intercepts native glCreateContext calls during boot and redirects them to headless EGL backends, removing the requirement to run desktop display servers inside the pVM.
Extended Gramine-VM LibOS: Augmented with 13 custom POSIX/SDL system calls (e.g., mremap) to support SDL-based Linux games inside Protected VMs without binary modifications.
B Host VMM & Presentation Sync
Lockless vGPU Listener (QEMU 10.1): Proxies GPU discovery and ioctl system calls via lockless ring buffers, eliminating host-guest thread contention for multi-threaded game engines.
Direct Presentation & Input Redirection: Presents GEM front-buffers directly to host X11/XWayland via xcb_present with fence sync, while an offscreen dummy window redirects host input events (XSelectInput).

Frequently Asked Questions

Common questions regarding performance overhead, threat boundaries, and compatibility.

How does Tirith maintain near-native rendering performance?

Tirith decouples high-throughput 3D GPU command submission from display output. OpenGL/Vulkan draw calls run via direct GPU pass-through inside the guest LibOS, while offscreen frame buffers are zero-copy shared with the host compositor.

What prevents a cheater from compromising the guest kernel?

The guest LibOS environment is cryptographically measured and signed. Any guest-level tampering invalidates the hypervisor attestation token before the game client connects to online matchmaking servers.

Why does Tirith translate OpenGL to EGL backends?

Native OpenGL contexts are tightly coupled with desktop display servers (X11). Including a full display server inside a secure guest VM increases the attack surface and overhead. EGL allows headless offscreen rendering without guest display integration.
